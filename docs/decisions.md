# Decisions

Implementation decisions that the spec leaves open, the answers to questions
raised while planning, and the results of verifications `SPEC.md` asks for.
The spec's own settled decisions are in its "Decisions" section and are not
repeated here.

## Answers to planning questions (14 Nov 2026)

The maintainer accepted the proposed defaults for all six questions.

| # | Question | Decision |
| - | -------- | -------- |
| Q1 | The rendered config header includes the UTC time, but rendering must be byte-identical for the same model. | The timestamp is an input to the renderer, like an injected clock. Golden tests fix it. Verify-staged compares against the exact bytes Auriga rendered. |
| Q2 | Huh input fields store values as `string`, which breaks the `[]byte`-only rule for secrets. | Seeds, sudo passwords and key passphrases use a custom masked-input component that writes into a `secret.Buffer`. Huh is used for every non-secret field. |
| Q3 | The M1 probe needs the redacted config read, which the build order lists under M3. | The read helper and on-host public-key derivation land in M1. Parsing and classification stay in M3. |
| Q4 | Checking `<archive-url>/.well-known/stellar-history.json` from the operator's machine would be a network call the security section forbids. | The check runs on the host with `curl`, through a helper script. |
| Q5 | Branching. | One branch and one pull request per milestone (`m0-scaffold`, `m1-ssh`, …), with small signed-off commits. |
| Q6 | Security contact and Homebrew tap. | Vulnerabilities are reported through GitHub private vulnerability reporting until a dedicated address exists. No tap until after v0.1. |

## Repository settings (15 Nov 2026)

| Setting | Value | Reason |
| ------- | ----- | ------ |
| Pull request creation | Collaborators only | Outside contributors take part through issues. |
| `main` ruleset | No deletion or force push; pull request required with 0 approvals, stale approvals dismissed and conversations resolved; `Lint, test, secrets, vuln` must pass on an up-to-date branch; repository admins may bypass for pull requests only | One maintainer cannot approve their own pull request, so required approvals would block every merge. |
| Merge methods | Merge commit and rebase; squash off | `CLAUDE.md` asks for small commits, which squash merging would collapse. |

| Web commits | Sign-off required | Matches the DCO requirement. |
| DCO | The DCO GitHub App checks every pull request, and its `DCO` check is required on `main` | Enforces `git commit -s` on pushed commits as well as web commits. |
| Not enforced | Signed (GPG or SSH) commits; actions pinned to commit SHAs | Not used yet; either can be turned on later. |

## M1 implementation decisions (16 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| Helpers run as `sudo -n -- sh -s -- <args>`, or `sudo -k -S -p '' -- sh -s -- <args>` with the password as the first stdin line. Whether a host needs a password is probed with exactly that command and the script `exit 0`. | `-k` makes sudo ignore cached credentials, so it always reads the password line. Without it, a cached credential would leave the password for `sh` to execute, and it could appear in an error message. Probing with the real command line detects a sudoers rule that only allows `sh`. |
| The redaction marker carries the full derived public key: `NODE_SEED = "<redacted:G…56 chars…> node-alias"`. | The key is public, and M3 needs it whole to parse and compare configs; the UI abbreviates it. |
| `StrictHostKeyChecking` `ask`, `accept-new`, `no` and `off` all prompt for unknown keys; only `yes` refuses without asking. | Hard rule 4: no way to turn off host-key checking. `accept-new` would add keys without the operator seeing the fingerprint. |
| A host whose known keys are all of other types than the one presented is treated as a changed key (hard failure). The client offers the known key types first, so this only happens if the server lost those keys. | Conservative: never prompt where OpenSSH would warn. |
| The ssh home directory is the one in the password database, not `$HOME`. | OpenSSH ignores `$HOME` for `~/.ssh/config`. Reading `$HOME/.ssh/config` for the alias list while `ssh -G` read the passwd home would resolve aliases against a different file; found when running the binary against the compose stack. |
| Auth failures, host key failures, ProxyCommand and invalid aliases stop automatic reconnects until the operator presses `r`. | Retrying cannot fix them, and repeated failed logins can trip fail2ban. |

## M2 findings from real stellar-core 30.0.0 (16 Nov 2026)

| Finding | Consequence |
| ------- | ----------- |
| `gen-seed` and `sec-to-pub` reject `--conf` ("Unrecognised token: --conf"); `version`, `http-command` and `new-hist` accept it. Without `--conf`, stellar-core reads `./stellar-core.cfg`, and relative `DATABASE` and `BUCKET_DIR_PATH` values resolve against the current directory (tested: `new-db` from `/etc/stellar` created `/etc/stellar/relative.db`). | **Correction to SPEC.md "CLI commands run on hosts" and CLAUDE.md** (agreed with the maintainer, 16 Nov 2026). Commands that read the config keep `--conf <config_path>` and run as `stellar` from the service's working directory (`auriga_core` in the helper prelude), so relative paths point where they do for the running node, and per-host config paths keep working. `gen-seed` and `sec-to-pub` read no config and run without `--conf`. Running everything from `/etc/stellar` without `--conf` was considered and rejected: it would put a relative-path database in the wrong place without any error. |
| The `stellar-core` package (stellar/packages) installs `/usr/lib/systemd/system/stellar-core.service`: `ExecStart=/usr/bin/stellar-core --conf /etc/stellar/stellar-core.cfg run`, `User=stellar`, and **no `WorkingDirectory`**, so systemd runs it from `/`. Its postinst runs `chown -R stellar:stellar /etc/stellar/ /var/lib/stellar/ /var/log/stellar/` on every configure. `stellar-core-utils` only adds `stellar-core-cmd` and `stellar-core-gap-detect`. | Helpers use the unit's `WorkingDirectory`, or `/` when unset, to match. The integration image mirrors the unit. For M5: a config Auriga writes as `root:stellar` becomes `stellar:stellar` after a package upgrade; treat that as expected, not as drift. |
| Listing a node in its own `[[VALIDATORS]]` with `NAME` equal to its `NODE_SEED` alias fails to start: "name already used". With siblings only and `QUALITY="MEDIUM"`, core builds a qset of all three nodes (`agree: 3`, `fail_at: 2`). | Supports the spec's "siblings only" decision. The `HIGH` three-validator count is still verified in M4. |
| Quorum and peers responses name nodes by their configured alias (`itest-b`) when known, otherwise by `G…` key. `info.quorum.node` is the alias. | The UI shows whichever it gets and maps known keys to inventory aliases. |
| `upgrades?mode=get` returns every field, with `{"nullopt": true}` for unset ones and `"time": 0` when nothing is scheduled. | The Upgrades tab hides unset fields. |
| `http-command` writes HTTP headers (`Content-Length`, `Content-Type`, then `\r\n\n`) before the body on stdout, and log lines on stderr. | The fallback strips the header block. |
| With the packaged unit (run from `/`), a config with relative paths fails: the default `LOG_FILE_PATH` is relative, and stellar-core exits with "Could not open log file … check access rights". SDF's `pubnet-validator-full` example uses absolute `LOG_FILE_PATH`, `BUCKET_DIR_PATH` and `DATABASE`. | Input for M3 and M4: when the unit sets no `WorkingDirectory`, validation warns about relative `LOG_FILE_PATH`, `BUCKET_DIR_PATH` and `sqlite3://` paths, and the wizard writes absolute ones. The integration configs use absolute paths. |
| `apt.stellar.org` publishes amd64 packages only. | The integration image is amd64; on arm64 machines Docker runs it under QEMU user emulation. |
| Recording 27.1.0 for decoding tests failed: a single-node SQLite setup exits with "Unable to setup the application to run". | Only 30.0.0 is recorded so far; the ledger-keyed quorum layout of older builds is covered by a synthetic fixture. |

## M3 decisions (16 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| Diffs use `github.com/aymanbagabas/go-udiff`. | SPEC.md names `hexops/gotextdiff` "or equivalent". go-udiff is its maintained fork with the same unified output, and it is already in the module graph through the golden-file test library. |
| Unknown top-level keys are rendered after the peers section and before the first table; unknown tables come last. | SPEC.md puts "preserved unknown keys" last, but TOML does not allow a plain key after a table header. Only their position changes; the text is kept verbatim (the `key = value` source, including comments inside multi-line arrays). Trailing comments on a line are dropped, like every other comment, and counted in the adoption notes. |
| A config is "unconfigured" when the file is missing or holds only comments. | The stellar-core package ships no `stellar-core.cfg`, only examples, so there is no package default to fingerprint (this settles the "package-default config fingerprint" verification). |
| `NODE_SEED` renders as `"<auriga-seed:MODE[:G…]> alias"`; the host reads it back as `"<redacted:G…> alias"`. | One marker form for the stage helper to replace (M5) and a fixed mapping for verifying the staged file. `Parse` refuses a plain seed. |
| Read-only triggers: the legacy `[QUORUM_SET]`, `HISTORY`/`VALIDATORS`/`HOME_DOMAINS`/`QUORUM_SET` as inline or dotted values, and unknown keys inside `[[VALIDATORS]]`, `[[HOME_DOMAINS]]` or `[HISTORY.*]`. Other unknown keys and tables keep a config adoptable. | These are the shapes the model cannot rewrite without changing their meaning. |
| `LOG_FILE_PATH = ""` is kept distinct from an absent key. | Empty turns file logging off; absent means the relative default, which fails under the packaged unit. |

## M4 decisions (16 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| Keys generated on a host are **pending** in the plan: siblings' `[[VALIDATORS]]` show `<generated at deploy: alias>` and the review says so. The deploy (M5) first runs `gen-seed` on every such host, keeping each seed in a root-only pending file on its host and returning only the public key, then re-plans with the real keys before staging anything. | Siblings must list each other's keys, so the keys must exist before any config is rendered. Generating them in the wizard would change hosts before the review, which SPEC.md forbids. |
| Configs the wizard writes for new nodes use absolute `BUCKET_DIR_PATH` (`/var/lib/stellar/buckets`) and `LOG_FILE_PATH` (`/var/log/stellar/stellar-core.log`); adopted hosts keep their values. | The packaged unit runs from `/` (M2 findings). |
| Both fixture orgs' renders, with test-vector seeds in place of the markers, are loaded into stellar-core 30.0.0 by the integration suite (`TestWizardRendersLoadInStellarCore`); all six are accepted. | Checks the generated configs against the real parser and quorum safety checks, not only golden files. |
| The per-host quorum override (step 7) replaces the org-wide trusted orgs and validators for that host with pasted entries, prefilled with the org-wide set. The host's own org (`NODE_HOME_DOMAIN` with the org quality) and its siblings are always kept, and pasted entries for the own domain are ignored. Quorum checks for an overriding host are reported at step 7. | Keeps the spec's "same set on every host by default", and stops an override from breaking the org's own entries, which come from steps 1, 4 and 5. |
| `UNSAFE_QUORUM` is an owned key. The wizard writes `UNSAFE_QUORUM=true` only when the generated quorum set tolerates no failures and the operator ticks a consent box in the quorum step (and types `pubnet` on pubnet). Agreed with the maintainer. | stellar-core 30.0.0 refuses to start ("SCP unsafe") when the top level of its quorum set tolerates zero failures, unless `UNSAFE_QUORUM=true`. SPEC.md only warns below four entities. The testnet acceptance scenario (own org + SDF testnet) always has that shape, as does the package's testnet example. Measured top levels: own org of 3 alone, 2 of 3 validators: accepted. Own org + 1 or 2 `HIGH` orgs, 2 of 2 or 3 of 3: refused. Own org + 3 `HIGH` orgs, 3 of 4: accepted. |
| The consent for `UNSAFE_QUORUM` also covers stellar-core's archive rule (M5): when a quorum can form without any validator that has a `HISTORY` archive, the quorum step asks for consent and, once given, writes `UNSAFE_QUORUM=true`. | Found deploying the wizard's render to the integration stack, an org of three Basic validators: core refused it ("validators with known archives should be included in all quorums", "SCP unsafe"). Core requires the archive-bearing validators to be v-blocking for the node's quorum set (`verifyHistoryValidatorsBlocking`, the node itself not counted). `internal/quorum` now computes the same, checked against core 30.0.0 with fixtures L to N (refused without archives; accepted with `UNSAFE_QUORUM`; accepted when three `HIGH` orgs with archives are trusted). |

## M5 decisions (16 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| Deploy: the rendered config travels to the host as a base64 argument of the stage helper; the seed never does. | The render holds only a seed marker, so it is not secret, and stdin is reserved for the one secret a helper asks for. A config is far below Linux's 128 KiB limit for one argument; the runner refuses anything over 120 000 characters. |
| Deploy: a seed generated on a host waits in a root-only `<config>.auriga-pending-seed` file until install consumes it; running the deploy again reuses it. | The plan must name the new key before anything is staged (see pending keys above), and a deploy interrupted between `gen-seed` and install must not create a second identity. |
| Deploy: stopping the wait at the sync gate marks the host "deployed, not yet synced" and stops a rolling deploy there; the remaining hosts are untouched. A failed quorum intersection after sync also stops the rollout without rolling back. | SPEC.md lets the operator stop waiting but rolls on only after a host passes the sync gate, so that two of three org nodes keep voting. An intersection failure is not a fault of the new config on that host, and restoring it would not fix the network. |
| Deploy: verify compares the staged file, read back with its seed redacted on the host, byte for byte with the reviewed render (or, for a manual rollback, with the backup as it was read for the diff), and install requires the installed sha256 to equal the verified one. | SPEC.md "Verify staged". The sha256 check also catches the file changing between verify and install. |
| Manual rollback stages the backup on the host with a new helper, `stage-backup`, then runs steps 4 to 10; its audit actions are `restore.<step>`. | The backup holds the real seed, so it is copied host-side rather than rendered. |
| The wizard starts each adopted host's archive from the `[HISTORY.*]` table it publishes to: as the nginx or S3 backend when that backend renders exactly the same table, otherwise as custom commands, with the URL taken from a `curl` get. An archive the host already publishes to (same name and put) gets no `new-hist`. | Without it a running Full validator had to re-enter its archive, and `new-hist` on an existing archive would erase it. |
| "Every node needs its own archive" compares public URLs (and S3 locations). Custom commands without a URL are not compared, and a custom get without a URL gets a warning when several hosts list each other. | The same `cp` to a local directory is the same text on every host but a different archive on each. Siblings use a node's get command as given, so a local path would read their own disk. |

## M6 decisions (17 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| The `http-command` fallback gets the query decoded (`upgradetime=2026-11-23T17:00:00Z`), the SSH tunnel and `curl` get it URL-encoded. The decoded form has its own allowlist (`:`, `+`, `/` and `=` added, still no shell characters). | Found arming the integration stack: `stellar-core http-command` passes its argument to the handler without URL-decoding it, so core refused `upgradetime=…%3A…` ("could not parse upgradetime"). |
| A failed `upgrades?mode=set`, `dumpproposedsettings` or `sorobaninfo` is detected from the body, not the status. | stellar-core 30 answers them with HTTP 200 and `{"exception": "…"}` or plain text ("could not parse upgradetime", "configUpgradeSet is missing or invalid"); success of set and clear is an empty body. |
| Arming is confirmed per host by reading back `upgrades?mode=get` (values compared field by field) and the `info` status line; a configupgradesetkey only needs to be reported as present. | SPEC.md step 5. The key's form in `mode=get` could not be recorded (that needs a published proposal), so only its presence is relied on. |
| "After arming" follows only votes armed in this session: when the ledger shows a vote's values (protocol, base fee and reserve, tx set sizes) it is recorded as `upgrade.applied`; when a host stops reporting it, `mode=get` is read and, if empty, re-arming with the same values is offered (`R`). | A restart or expiry can drop a vote; Auriga keeps no secrets or votes on disk, and the vote's values are in the audit log. Re-arming a value the ledger already has stays armed until it expires (seen on core 30), so "applied" is judged from the ledger, not from the status line disappearing. |
| The spec's "the dashboard shows the new value" is the upgrades overview (base fee and reserve columns from the polled `info`) and the dashboard's protocol column; the integration test checks the polled `info`. | The dashboard has no base fee column at 80 columns; SPEC.md puts base fee and reserve in the upgrades overview. |
| The Soroban inspector compares settings by `configSettingID` wherever they appear in either document, field by field. | `sorobaninfo?format=detailed` (recorded from core 30) lists `ConfigSettingsEntries`; a real `dumpproposedsettings` answer could not be recorded without a published proposal, so the comparison does not depend on its wrapper. |
| The integration suite upgrades the stack's network from protocol 0 to 30 (with two of three validators armed it applied within seconds). | It exercises `protocolversion` on real hosts and turns on Soroban, so `sorobaninfo` and `dumpproposedsettings` can be called. |

## M7 decisions (17 Nov 2026)

| Decision | Reason |
| -------- | ------ |
| With `NO_COLOR`, the finished frame goes through `theme.StripColour`, which removes colour parameters from every SGR sequence and keeps bold, faint, reverse and underline. huh forms show the focused button in reverse video. | A check added to every app test (each frame fills 80×24 exactly and sets no colour under NO_COLOR) found huh's text inputs, cursor and buttons colouring the wizard and upgrades forms. huh's theme cannot reach the blurred text-input styles, so the frame is cleaned in one place. |
| The fallback helper refuses an admin query whose decoded value holds `&`, `?` or `#`. | `FuzzRawCommand` found that decoding for `http-command` turned `configupgradesetkey=x%26mode%3Dclear` into an extra `mode=clear` parameter. Arming already rejects such a key (it is not base64), so this was not reachable from the UI, but the helper layer now refuses it on its own. |
| The recommended sudoers rule is `ALL=(root) NOPASSWD: /bin/sh -s --*, /usr/bin/sh -s --*`, and the integration hosts that need no password use exactly that. | Helpers are scripts fed to `sh -s` on stdin, so sudo cannot narrow them further. The rule is documented as a root shell, and the suite proves Auriga needs nothing beyond it. |
| Release builds are reproducible (`-trimpath`, commit timestamps, no build date). The SBOMs are not byte-identical between runs. | Two snapshot builds of the same commit gave identical archives and binaries. syft writes a creation time and a unique document namespace into each SPDX file. |

The release job runs only after lint, tests, fuzzing and the integration suite pass on the tag, and creates a draft. | The repository allows only GitHub-owned actions (and golangci-lint's), and the first push of the job with third-party actions failed to start. `go install` verifies the sources against the Go checksum database. A maintainer reads the draft before anyone can download it. |
| The demo GIF is recorded with VHS against the Docker integration stack (`docs/demo/`), with the hosts renamed `acme-a`, `acme-b` and `acme-c` in a throwaway `~/.ssh/config`. | It shows real stellar-core 30 nodes without pointing anything at testnet or pubnet. |
| A connected node whose fresh `info` reports `Synced!` is labelled "synced" in the host detail header, even when its health is degraded or down. The symbol, colour and status line still show the health. This departs from the plain ok/degraded/down words in SPEC.md's UX section, at the maintainer's request. | A synced node with too few peers read "○ down", which suggests the node is not running. The word now says what the node is doing, and the problem stays visible as the red symbol and the line naming it. Stale info, a failed last poll or a lost connection still show the health word. |
| The first release is `v1.0.0`, not `v0.1.0`, and it is preceded by release candidates (`v1.0.0-rc.N`). The manual acceptance runs on the release candidate's signed archives, and adds an item (13) that checks the release workflow's output. SPEC.md's release and M7 lines are updated to match. | The maintainer's decision (19 Nov 2026). Running acceptance on the CI-built artefacts tests the release job, which never runs on pull requests, before the final tag. |

| The release job installs its tools with `GOTOOLCHAIN=auto`, and only in that step. | GoReleaser v2.19.0 needs Go 1.27.3 and cosign v3.1.4 needs Go 1.27, while setup-go pins the job to the repository's Go 1.26 with `GOTOOLCHAIN=local`. The first `v1.0.0-rc.1` release job failed for this reason. The fetched toolchain is checked against the Go checksum database, and the GoReleaser step still builds Auriga with the toolchain in `go.mod`. |
| `.goreleaser.yaml` does not set `changelog.disable`. Release notes come only from `--release-notes`. | With `disable: true`, GoReleaser v2.19.0 skips the whole changelog pipe, which is also the pipe that loads `--release-notes`, so `v1.0.0-rc.2`'s draft had an empty body. Given a notes file, the pipe uses it and returns before building a changelog from git (`internal/pipe/changelog/changelog.go`, checked with a local tagged release run). |
| Host detail tabs switch with `←` and `→`, at the maintainer's request (SPEC.md's key table updated). `tab` and `shift+tab` still work there but are no longer shown; the wizard keeps `tab` for fields and hosts. | Nothing else in host detail uses the horizontal arrows, and they match the tab bar's layout. |

| Node names in `quorum` responses are shown whole. Only valid public keys are abbreviated. | stellar-core reports nodes by their config names when it has them (the recorded 30.0.0 responses use `itest-a`), and abbreviating a name such as `sdf_testnet_1` to `sdf_…et_1` hid it. |

## Verifications

| Item | Milestone | Result |
| ---- | --------- | ------ |
| How stellar-core counts the three-validator minimum for a `HIGH` org when a node lists only its siblings | M4 | **Siblings only is correct, and the only form that works.** Checked on stellar-core 30.0.0 by loading configs with `new-db` (16 Nov 2026): `HIGH` with two siblings that have `HISTORY` is accepted, and core adds the node itself (generated qset `{"t":2,"v":["itest-b","itest-a","itest-c"]}`). `HIGH` with one sibling is refused ("must have redundancy of at least 3": self + 1 = 2). A `HIGH` sibling without `HISTORY` is refused ("critical and high quality must have an archive"). Listing the node itself is refused under its `NODE_SEED` alias ("name already used") and under any other name ("naming node twice"). The node itself needs no `HISTORY` entry. |
| The helper-script stdin protocol (script, sudo password and seed on one stdin) works under dash and bash | M1 | **Changed.** dash reads a piped script in large blocks, so a secret placed after the script was swallowed by the parser and never reached the helper's `read` (bash reads byte by byte and worked). The runner now sends the secret only when the helper asks for it: `auriga_read_secret` prints a request line, and the runner writes the secret after seeing it. sh has finished reading the script by then, and a helper that never asks never receives the secret. The command stays `sudo … sh -s -- <args>`. Tested under dash and bash with the sudo shim (2026-11-16); real hosts are checked in the compose suite. |
| `ssh -G` output across OpenSSH versions | M1 | OpenSSH 10.0 prints `StrictHostKeyChecking yes` as `true` (and `no` as `false`); the parser normalises both. 10.0 output is recorded in `internal/sshx/testdata/`; Ubuntu 24.04's OpenSSH 9.6 is added with the compose suite. |
| Package-default config fingerprint from `apt.stellar.org` | M3 | The package installs no `stellar-core.cfg` (only `stellar-core_example*.cfg` and others in `/etc/stellar`), so unconfigured means missing or comments only. |
| `expirationminutes` acceptance by stellar-core build | M6 | **Accepted by stellar-core 30.0.0**, checked on the integration stack (17 Nov 2026): `upgrades?mode=set&…&expirationminutes=30` arms, `mode=get` reports `"expirationminutes": {"data": 30, "nullopt": false}`, and the integration suite arms with it on every run. As SPEC.md decided, Auriga sends it only when the operator fills the field; older builds are not checked. |
